# 验证规则：给AI，也给自己

> 对应《驾驭AI编程》第5章。可将适用规则合并到项目规则文件，并确认工具实际读取了它。

## 可合并到项目的规则

```text
- 测试失败时默认修代码，不得为了变绿而删测试、降低断言或跳过失败。
- 确需改测试，先说明需求变化或测试本身的错误，按已有授权或经确认后修改。
- 按改动风险选择验证，覆盖关键行为、边界和失败路径；不以测试数量代替覆盖质量。
- 完成项目要求的构建、测试和检查。说明实际执行的命令、结果及未验证范围。
- 发现已有失败时，区分基线问题与本次引入的问题，不隐藏失败。
- 不把AI解释、静态检查通过或局部测试通过，直接当作整体交付完成的证据。
```

## 检查是否有效

- [ ] 测试预期来自需求或独立契约，而非照抄实现。
- [ ] 失败路径有明确预期；测试失败时查明是实现、需求还是测试的问题。
- [ ] 需要运行环境或人工操作的部分已实际验证，或明确列为未验证。
- [ ] 日志、截图和测试结果可以定位到本次代码与环境，且未泄露敏感信息。

## 给自己的提醒

- **解释用来帮助理解。** 看不懂可以让AI反述行为，再与需求、代码和运行证据比较；讲得通不保证做得对。
- **重复失败先停下来诊断。** 若没有获得新证据，不要继续叠补丁。先判断问题在代码、设计还是需求。
- **回退前保护现有工作。** 先查看差异和未提交内容，明确要恢复的范围；本地恢复与撤销共享提交使用不同流程，不机械执行`reset`或`revert`。
- **在有意义的节点保存基线。** 大改前和一个可验证步骤完成后，按项目约定留存快照或提交；不要以固定分钟数代替判断。
