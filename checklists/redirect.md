# 校准流程 Checklist

> 对应《驾驭AI编程》第6章。先判断偏差在哪一层，再决定怎样改。

## 先定位偏差

- [ ] **代码层：** 需求和设计明确，但实现不符。提供复现步骤、期望结果、实际结果和必要日志。
- [ ] **设计层：** 局部修补不断引出新问题。重新检查模块边界、数据流和关键取舍。
- [ ] **需求层：** 各方对“做成什么”理解不一致。先澄清目标和验收条件，再继续实现。

## 给出可执行反馈

- [ ] 指出具体偏差及依据，不只说“不对”“再想想”。
- [ ] **相关问题一起校准，无关问题分开处理。** 避免拆散同一个根因，也避免把多个不相关目标塞进一轮。
- [ ] 说明哪些原有决定仍然有效，哪些被本次反馈替代。
- [ ] 要求先提出可验证的原因假设，再决定改动；不让猜测直接变成一批补丁。

## 判断是否换路径

- [ ] 连续尝试是否获得新证据？若反复走回同一路径，先停止修改，重新定位问题。
- [ ] 是缺少项目背景、规格含糊、测试不可靠，还是实现能力不足？换模型不能替代补齐信息。
- [ ] 历史对话是否持续干扰当前任务？需要时整理[交接记录](../templates/handoff/HANDOFF.md)，让新会话读取当前代码和有效决定。
- [ ] 必要时引入另一位审阅者、换模型或手工处理局部难点，并用同一验收条件比较结果。
- [ ] 如需回退，先保护未提交工作，确认目标版本和影响范围；不要按固定失败次数自动清空改动。

## 把经验留下

- [ ] 验证原问题是否消失，以及是否引入新问题。
- [ ] 用[翻车记录](crash-log.md)保留证据、原因判断和处理结果。
- [ ] 只有可复用的教训才转成规则、测试或权限控制；按项目的授权与审查流程更新，并检查是否实际生效。
