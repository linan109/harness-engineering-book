# 代码考古 Prompt
> Code Archaeology — Understand Legacy Code Before Changing It | 来源：《驾驭AI编程》第7章

## 使用场景
- 接手一个陌生代码库，需要快速建立对模块的理解
- 准备重构或修改遗留代码，需要先识别隐式依赖和"看起来丑但有原因"的代码
- 新团队成员 onboarding，用 AI 辅助阅读代码加速理解

## 基础版本

```
请阅读 src/payment/ 目录下所有文件，并回答以下问题：
1. 这个模块的核心数据流是什么？（一个请求从入口到数据库经过哪些层）
2. 有哪些看起来像临时补丁的代码？（但先别急着说该删除）
3. 有哪些隐式依赖？（全局状态、环境变量、特定的调用顺序、反射调用等）
4. 同一个逻辑是否被实现了多次？（重复代码可能意味着不同时期的不同需求）
```

> AI 的回答不会完全正确，但你修正它的过程，就是建立理解的过程。当你说"这不是临时补丁，而是三年前的合规要求"时，一条原本只存在于某个离职员工脑海中的知识就被显式化了。

## 变体

### 维护场景：定点考古

当你只需要修改某个具体功能，不需要理解整个模块时使用。

```
请阅读 src/billing/invoice_generator.py 及其直接依赖文件，回答以下问题：
1. 这个文件的核心职责是什么？输入输出分别是什么？
2. 它依赖哪些外部服务或配置？（API 调用、环境变量、配置文件）
3. 有哪些硬编码的数值或字符串？它们分别代表什么含义？
4. 这个文件最近一次 git 修改是什么时候？修改了什么？（如果能看到 git log）

注意：不要建议任何修改，只做分析。
```

### 重构场景：边界与耦合分析

准备重构时，重点识别模块边界和耦合关系。

```
请阅读 src/order/ 目录下所有文件，回答以下问题：
1. 这个模块对外暴露了哪些接口？（public API、HTTP endpoint、消息队列消费者等）
2. 它调用了哪些其他模块的代码？被哪些其他模块调用？
3. 有哪些跨模块的共享状态？（共用数据库表、全局变量、缓存 key 等）
4. 如果要把这个模块完全独立出去，最大的阻碍是什么？

请以列表形式输出，每个依赖关系标注方向（调用/被调用）和耦合强度（强/中/弱）。
```

### 紧急故障场景：快速定位

线上出问题时，跳过全面考古，直奔故障相关代码。

```
线上报错：[粘贴错误信息]

请阅读 src/payment/checkout.py，回答：
1. 这个报错最可能从哪一行抛出？
2. 触发这个错误需要什么条件？
3. 最近这个文件有没有被修改过？（如果能看到 git log）
4. 这个错误会影响哪些下游流程？

只做分析，不要修改任何代码。
```

## 使用技巧

- **保持只读纪律**：代码考古阶段绝对不要让 AI 修改任何文件。先理解，再动手。在 prompt 末尾加"不要建议任何修改，只做分析"可以减少 AI 的"顺手改"倾向。
- **修正即知识沉淀**：AI 犯的每个错误都在暴露一条系统暗规则。把修正结果写入项目配置文件（CLAUDE.md / AGENTS.md），后续所有 AI 对话都能受益。
- **分清两种盲区**：自己团队的老项目，真正危险的不是完全陌生的代码，而是"我们以为懂但没人真正验证过"的部分。让 AI 读这些模块，对照它的理解做检查，往往会发现意外。
