# 特征化测试 Prompt
> Characterization Test — Test What IS, Not What SHOULD BE | 来源：《驾驭AI编程》第7章

## 使用场景
- 准备修改遗留代码，需要先给现有行为"拍快照"，确保改动不会破坏已有功能
- 接手没有测试覆盖的模块，需要在动手前建立安全网
- 技术栈迁移前，需要生成"黄金快照"用于迁移后的行为一致性比对

## 基础版本

```
请阅读 src/billing/calculator.py 文件，并为该模块编写测试。
注意：不要测试"应该"怎样，而是测试"现在"怎样。
包括边界情况和看起来奇怪的行为。
如果现有行为看起来像bug，也将其写成测试，并添加注释标注"疑似bug，待确认"。
```

> 当规格说明与实际行为冲突时，以实际行为为准。因为线上用户依赖的是实际行为，而非文档。这种测试的作用是保证行为不退化。

## 变体

### 维护场景：局部安全网

只需要修改某个模块的某个功能，重点测试改动区域及其上下游。

```
请阅读 src/billing/calculator.py 文件，重点为以下函数编写测试：
- calculate_discount()
- apply_tax()

要求：
1. 测试"现在"的行为，不是"应该"的行为
2. 覆盖每个函数的正常路径和边界条件
3. 测试这两个函数与调用它们的上游函数之间的交互
4. 如果发现看起来像 bug 的行为，写成测试并标注 "疑似bug，待确认"
```

### 重构场景：全面行为快照

准备重构整个模块时，需要更高的测试覆盖率。

```
请阅读 src/billing/ 目录下所有文件，为该模块编写特征化测试套件。

要求：
1. 覆盖所有 public 方法
2. 每个方法至少包含：正常输入、边界值、空值/异常输入
3. 测试模块内部函数之间的调用链（A 调 B 调 C 的完整路径）
4. 不要 mock 模块内部的依赖，只 mock 外部服务
5. 如果现有行为看起来像 bug，写成测试并标注 "疑似bug，待确认"
6. 测试命名格式：test_函数名_输入条件_期望结果

目标是：重构后跑这套测试，全绿就说明行为没变。
```

### 技术栈迁移场景：黄金快照

迁移前生成输入到输出的完整映射，迁移后逐条比对。

```
请阅读 src/billing/ 目录下所有文件，生成"黄金快照"测试。

要求：
1. 为每个 public API 准备一组固定输入，记录当前的精确输出
2. 输出包括：返回值、副作用（数据库写入、文件生成、API 调用等）、日志输出
3. 使用 snapshot testing 或直接硬编码期望值
4. 特别关注：浮点数精度、日期格式、字符编码、null 处理
5. 边界情况的行为要逐条记录——迁移后这些地方最容易悄悄变化

这些测试在迁移后将逐条比对，任何差异都需要人工确认。
```

### 紧急修复后：补测试

故障修复后，把修复本身变成一条回归测试。

```
刚刚修复了一个线上 bug：[简述 bug 和修复内容]

请为这个修复编写回归测试：
1. 一条测试复现原始 bug 的触发条件，验证现在不会再崩溃/出错
2. 测试修复后的正确行为
3. 测试相邻的边界条件（修复点附近的其他输入）
4. 添加注释说明这条测试对应的 bug 和修复日期
```

## 使用技巧

- **先测后改，严格顺序**：修改代码前跑一遍测试，修改后再跑一遍。只要测试通过，就说明没有破坏已有行为。至于已有行为是否正确，那是另一个问题，后续再处理。
- **"疑似 bug"不要直接修**：特征化测试的目的是锁定现状，不是改善现状。标注"疑似 bug"的测试先保留，等安全网建好后再决定是否修复。
- **不要让写代码的 AI 在同一个会话里写测试**：裁判和运动员是同一个人，比赛结果没有悬念。用独立会话或另一个 AI 来写测试，确保测试的独立性。
